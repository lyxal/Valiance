# Nominal identity across module boundaries (pre-0.1 repairs)

## Guaranteed by the repaired import paths

- A public imported object may be renamed multiple times. Its *type-system*
  origin remains the declaration in its original provider; a re-export is not
  a new nominal type.
- Callable interfaces record the origins of the imported nominal spellings
  used in their signatures (including generic arguments). Consumers resolve
  those origins against the visible selected aliases, rather than comparing
  short type names or treating unrelated providers as interchangeable.
- A generic function whose body must be re-checked at its call site (for
  instance, because it performs checked reflection) has the same nominated
  aliases applied to the nominal annotations in that body and its signature.
  The receiver and reflection descriptor therefore use compatible type names.
- Runtime object destructors remain **private lifecycle hooks**. Facade
  imports compile them against their actual receiver binding and deduplicate
  repeated imports by source declaration identity, not by imported spelling,
  generated bytecode, or the order in which modules were loaded. Checked
  implementations win over equivalent source-form replays.
- Independent providers defining identically named objects remain distinct;
  matching structural fields are not evidence of nominal equality.

## Persisted interface and cache rules

`ModuleDefinition.private_nominals` is a historical field name. It now includes
**all relevant imported nominal origins**, not only private types. The
semantic interface hash includes this mapping, so origin-only changes can
invalidate compiled consumers even when a printed function signature does not
change. `COMPILER_ABI=8` and `INTERFACE_ABI=7` require a clean rebuild of
older `.vbcm` dependency caches.

## Scope of verification

- Two original regression cases in both source-only and compiled-only modes.
- Deep facade renaming with generic reflection, with source/binary/mixed
  layouts; four VM execution modes per layout.
- Repeated destructor renaming through multiple public facades, with exact
  output counts and the same artifact layouts.
- Independent same-short-name providers with distinct final-release output.
- Negative generic reflection overload selection across providers.
- Cache-key sensitivity to changes in provider origin metadata.
- Existing module import, package identity, serialization, and focused runtime
  lifecycle suites (recorded in the separate validation JSON).

## Incomplete work and open semantic design question

This is **not** a full first-class canonical nominal identity implementation
across every VM value and instruction. Runtime `ObjectValue.type_name` may still
reflect the current imported spelling. The wider design should distinguish
canonical provider identity (for equality, dispatch, reflection and
serialization) from display spelling (for source diagnostics). The proposed
semantic rule is that aliases never change nominal identity; the choice of
how much provider qualification to expose in user-visible reflection remains
open for language specification review.

Full repository and Python 3.14+ verification remain necessary before the
broader pre-release certification gate can be considered complete.
